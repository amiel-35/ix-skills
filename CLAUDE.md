# Contribution Guide — ix-skills

ix-skills holds **cognitive atoms**: gestures that apply to any content
(critique, decision, explorer, fact-check…) and advisory postures (red-team,
contrarian…). Domain skills — those that rely on domain knowledge that can go
stale (law, HR practice, finance, product methods) or produce an artefact a
profession defines (PRD, NDA, job description) — live in
[ix-recipes](https://github.com/amiel-35/ix-recipes), along with workflows that
chain the atoms.

**Dependency rule: ix-recipes depends on ix-skills, never the other way round.**
An ix-skills skill must never point to an ix-recipes skill (a user may have
ix-skills alone). Skill ids stay unique across both repos (the legacy Codex installer copies them
flat into `~/.codex/skills/`, and a bare id is ambiguous to users). `build.py` is duplicated in ix-recipes: carry
any fix over to the other copy.

## 1. Repo structure

| Path | Role |
|---|---|
| `skills/` | Canonical source: one `.md` file per skill + `.mystaffy.json` override files |
| `dist/` | Plugin root: `.claude-plugin/plugin.json` + `skills/<id>/SKILL.md` Agent Skills artifacts for Cowork/ChatGPT Skills — **committed**, skills generated by `build.py`, exception to the no-generated-files rule (see §7) |
| `mystaffy-dist/` | mystaffy artifacts — gitignored, generated by `build.py` |
| `dist/.claude-plugin/plugin.json` | Plugin manifest for Claude Code / Cowork (hand-maintained, inside the plugin root) |
| `.claude-plugin/marketplace.json` | Marketplace manifest — lets the repo be added via Cowork "Ajouter depuis un dépôt" / `claude plugin marketplace add owner/repo`; points at `./dist` |
| `partials/` | Reference annexes (English) copied into `dist/skills/<id>/references/` for the skills that list them in `references` |
| `build.py` | Single entry point for packaging skills |
| `requirements.txt` | Python dependencies (`jsonschema`, `pyyaml`) |

---

## 2. Canonical skill format

Each `skills/<id>.md` file starts with a YAML frontmatter block.

### Required fields

| Field | Type | Description |
|---|---|---|
| `id` | string | kebab-case, matches the filename exactly |
| `label` | string | Display name (in French) |
| `version` | string | semver (`x.y.z`) |
| `description_fr` | string | Triggers + what the skill does / does not do (in French) |
| `description_en` | string | Same in English |
| `icon` | string | Emoji or unicode character |
| `domain` | string | Domain tag — see section 6 |
| `input_types` | string[] | Accepted input types |
| `output_types` | string[] | Produced output types |
| `compatible` | string[] | Always `[claude-ai, claude-code, cowork, gpt, gemini, mystaffy]` |

### Optional fields

| Field | Type | Description |
|---|---|---|
| `category` | string | mystaffy atom type: `atome`, `research`, `critique`, `decision`, `production`, … |
| `references` | string[] | Files of `partials/` copied into `dist/skills/<id>/references/` by `build.py`; the body says which one to read when (progressive disclosure: the model reads only the file it needs). Used by `prioritize` (one file per framework), `deliver` (HTML, recipient profiles), `critique` (lens selection) |
| `aliases` | string[] | Alternative names for the skill |

### Body

The body (everything after the frontmatter) is written **entirely in English**. It describes the role, rules, method, constraints, and output format of the skill.

---

## 3. Naming rules

- `id`: lowercase, kebab-case, matches the `.md` filename **exactly**
- No spaces, no accented characters in ids
- Breaking change → bump **major** version
- New feature → bump **minor** version
- Bug fix → bump **patch** version

---

## 4. Checklist — adding a new skill

1. Check the placement rule above (cognitive atom here, domain skill in ix-recipes) and that the id is free in ix-recipes
2. Create `skills/<id>.md` with complete canonical frontmatter
3. Write the body in English
4. Create `skills/<id>.mystaffy.json` with `category`, `params`, `ui` (minimum)
5. Test: `python3 build.py <id> --validate`
6. Build: `python3 build.py <id>` — this also (re)writes `dist/skills/<id>/SKILL.md`, which must be committed
7. No `dist/.claude-plugin/plugin.json` edit needed: skills are auto-discovered from the
   default `skills/` layout inside the plugin root, so any `dist/skills/<id>/` directory
   with a `SKILL.md` is picked up automatically

---

## 5. Checklist — adding a new domain

1. Choose a `domain` slug (lowercase, from the list in section 6)
2. Add the mapping to the `DOMAIN_TO_METIER` table in `build.py`
3. Document the domain in section 6 of this file

## 7. Packaging targets

| target | description |
|---|---|
| `agentskills` | `dist/skills/<id>/SKILL.md` — Agent Skills format (name/description frontmatter) for Claude Cowork and ChatGPT Skills; plus `dist/skills/<id>/references/` for skills that list `references` |
| `cowork` | validates `dist/.claude-plugin/plugin.json` |
| `mystaffy` | `mystaffy-dist/<id>/` (no `references/`) |
| `ix-memory` | `mystaffy-dist/<id>/` — native ix-memory format (manifest.json + skill.md, no `references/`) |
| `codex` | `codex-dist/<id>/SKILL.md` — Codex CLI format (name/description/triggers frontmatter); plus `codex-dist/<id>/references/` |

`agentskills` replaces the former `claude-ai` target, which zipped the raw `skills/<id>.md`
without transforming the frontmatter (invalid `.skill` output). It emits open
`dist/skills/<id>/` directories rather than zips: upload one as-is in **Cowork → Customize**,
in the **ChatGPT Skills** editor, or zip the folder yourself if a `.skill` archive is needed.

### `dist/` is the plugin root — canonical layout only

`dist/` holds the plugin manifest (`dist/.claude-plugin/plugin.json`) and skills in the
**default** `skills/<id>/SKILL.md` layout, with **no custom `skills` field** in `plugin.json`
and the marketplace `source` pointing at the `./dist` subdirectory (not `./`). This is
deliberate: the Cowork/claude.ai web marketplace validator is stricter than the Claude Code
CLI — plugins declared at the repo root and custom `skills` path arrays sync fine via the CLI
but fail on claude.ai. Do not move the plugin back to the repo root or reintroduce a `skills`
field.

The `amiel-35/plugins` catalogue marketplace (marketplace name `amiel-35`, listing ix-skills,
ix-recipes and ghost-council) points at this repo with a `git-subdir` source: `path: dist`,
`ref: main`. Moving `dist/`, renaming the plugin or switching the default branch breaks it.
It works in the Claude Code CLI; acceptance by Cowork "Add from repository" is not tested yet,
so the repo's own marketplace stays the documented Cowork path.

### `dist/` is committed, not gitignored

Unlike `mystaffy-dist/` and `codex-dist/`, **`dist/` is tracked in git** — this is a deliberate
exception to the "no generated files" rule (§9). Claude Code plugin/marketplace installs
resolve paths against the repo as checked out from git, not against a local build step a user
runs — so for "Ajouter depuis un dépôt" (Cowork) or `claude plugin marketplace add owner/repo`
to work, the `dist/skills/<id>/SKILL.md` files a consumer's Claude Code installs from have to
already be in the repo (`references/` subfolders included). Whenever a skill or a partial changes, rebuild
(`python3 build.py --target agentskills`) and commit the updated `dist/` output in the same
change. `dist/.claude-plugin/plugin.json` is hand-maintained (build.py validates it via the
`cowork` target but never writes it).

Validate the plugin with `claude plugin validate dist` (requires the Claude Code CLI).

```bash
python3 build.py                              # all targets, all skills
python3 build.py <id>                         # specific skill, all targets
python3 build.py --target agentskills         # dist/skills/<id>/SKILL.md for Cowork + ChatGPT Skills
python3 build.py --target cowork              # validate dist/.claude-plugin/plugin.json
python3 build.py --target mystaffy            # mystaffy-dist/<id>/
python3 build.py --target mystaffy --domain cognitif
python3 build.py --target ix-memory           # mystaffy-dist/<id>/ — ix-memory format
python3 build.py --target codex               # codex-dist/<id>/SKILL.md — Codex CLI format
python3 build.py --validate                   # validate without writing
```

### Installing into Codex

Primary method (tested 2026-10-14, codex-cli 0.155.1): Codex reads the Claude-format marketplace
directly, so `dist/` needs nothing extra:

```bash
codex plugin marketplace add amiel-35/ix-skills
codex plugin add ix-skills@ix-skills
```

Skills land in `~/.codex/plugins/cache/ix-skills/ix-skills/<version>/skills/<id>/` with their
`references/`. Users must name the skill in the request; an unnamed request did not trigger it. The
`amiel-35/plugins` catalogue (`git-subdir` sources) is untested with Codex. Antigravity (`agy`) is
covered the same way: `agy plugin import <clone>/dist` (not `validate`/`install`, which expect a
root `plugin.json`). Keep README.md and README-fr.md in sync when this changes.

Legacy method (not re-tested on Codex 0.155), copies into `~/.codex/skills/`:

```bash
bash scripts/install-codex.sh                 # build + install all skills
bash scripts/install-codex.sh <id>            # build + install one skill
bash scripts/install-codex.sh --dry-run       # preview: nothing written to ~/.codex
```

Skills are installed to `~/.codex/skills/<id>/SKILL.md`, with their `references/` subfolder when
they have one. The script runs `build.py --target codex` first (with the `python3` on `PATH`, which
needs `jsonschema` and `pyyaml`; `--dry-run` still rebuilds the gitignored `codex-dist/`), and
installs everything found in `codex-dist/` when no id is given. Restart Codex to activate.

### References (`partials/`)

A skill lists files of `partials/` in its `references` frontmatter field; `build.py` (targets
`agentskills` and `codex`) copies them into `<skill>/references/`, rebuilt from scratch on each
build, and the skill body tells the model which one to read when. Where they travel: Claude Code /
Cowork plugin installs, Codex plugin installs and `install-codex.sh` carry them; uploading a single `dist/skills/<id>/`
folder carries them only if `references/` is uploaded with it; the `mystaffy` / `ix-memory`
targets and pasting `skills/<id>.md` into GPT/Gemini do not. A skill with `references` should say in
its body what to do when the folder is missing (a pasted skill has none). Partials are English,
like skill bodies.

### Extending build.py for a new target

1. Add the value to the `choices` of the `--target` argument
2. Create a `build_<target>(skill_id, ...)` function in `build.py`
3. Call it from `main()` based on the selected target

---

## 8. Contribution rules

- Skill bodies are **in English**
- `label`, `description_fr`, `description_en` and any `README.md` are **in French** (or bilingual)
- One skill = one source file in `skills/`
- No business logic in skills — skills are prompts, not code
- No external dependencies in `build.py` except `jsonschema` and `pyyaml`
- `mystaffy-dist/` and `codex-dist/` are gitignored — never commit them
- `dist/` is the one exception: it **is** committed (see §7) — always rebuild and commit it alongside any skill change

---

## 9. What we do NOT do

- No conditional logic, API calls, or side effects in skills
- No external dependencies in `build.py` (except `jsonschema` and `pyyaml`)
- No generated files in the repo except `dist/` (`mystaffy-dist/`, `codex-dist/` stay gitignored — `dist/` is committed so Cowork/ChatGPT can install straight from the repo, see §7)
- No skill ids with accents or uppercase letters
